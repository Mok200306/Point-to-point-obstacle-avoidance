# 项目演进与阶段复现总览

更新时间：2026-08-22

本文是项目从最初的 A->B 仿真调试走到当前五点闭环验证的总入口。它回答三个问题：

1. 每个阶段遇到了什么问题，做了什么改进；
2. 哪些方法已经验证，哪些只适用于历史对照；
3. 如何按对应 Git 提交和结果目录复现历史阶段。

## 1. 当前结论

当前推荐算法是 `adaptive_goal_line_045`，运行环境为 Ubuntu 20.04 主机、Docker 内
Ubuntu 22.04、ROS 2 Humble、Gazebo、RTAB-Map online SLAM 和 Nav2。传感器只有
Gazebo RGB-D 点云，没有使用真实或仿真的 `/scan`。

在 `indoor_obstacle_course_large.world` 中，当前算法完成了三种五点闭环顺序的独立验证：

| 闭环顺序 | 完整 run | 分段成功 | 平均 wall 时间 | 平均 Gazebo 轨迹 | 非地面 contacts |
| --- | ---: | ---: | ---: | ---: | ---: |
| M->A->B->C->D->M | 3/3 | 15/15 | 288.563 +/- 7.516 s | 51.919 +/- 0.877 m | 0/3 |
| C->A->D->B->M->C | 3/3 | 15/15 | 296.649 +/- 2.088 s | 49.714 +/- 0.041 m | 0/3 |
| B->M->A->C->D->B | 3/3 | 15/15 | 325.836 +/- 2.538 s | 58.005 +/- 0.023 m | 0/3 |

合计为 `9/9` 完整 run、`45/45` 目标段、`0/9` 过滤地面后的非地面物理接触。
这证明了当前 profile 在这个静态大场景中可以在线建图、按当前目标实时规划并连续
完成多目标闭环。它不等于已经证明任意未知房间、任意窄通道或真实 D435i 都能保证
成功。

统一验收数据和轨迹图见
[点位顺序跨实验统一分析_2026-08-22.md](../06_五点闭环与顺序验证_2026-08-22/点位顺序跨实验统一分析_2026-08-22.md)，
最终边界见 [当前场景算法最终验证总结_2026-08-22.md](../06_五点闭环与顺序验证_2026-08-22/当前场景算法最终验证总结_2026-08-22.md)。

## 2. 统一工具链

```text
Gazebo RGB-D
  -> RTAB-Map online SLAM -> /map, map->odom
  -> map_padder -> /nav_map
  -> Nav2 global costmap + RGB-D obstacle layer + inflation
  -> GoalLineSmacPlanner / SmacPlanner2D
  -> Regulated Pure Pursuit
  -> velocity_smoother
  -> collision_monitor -> /cmd_vel_safe
  -> TurtleBot3 Waffle
```

当前通用 profile 的关键点：

- `online=true`、`localization=false`、`reset_db=true`，每次从空数据库开始在线建图；
- 每个目标创建新的 `NavigateToPose` action；
- 每次规划使用当前机器人位姿、当前目标和当前 live costmap；
- `line_bias` 只提供当前起点到当前目标直线的软偏好；
- `side_bias=false`，关闭 v4 的固定世界坐标走廊先验；
- `inflation_radius=0.45 m`，RPP 目标速度 `0.28 m/s`；
- footprint 为 `0.60 x 0.48 m`，collision monitor 继续作为最后的速度安全层。

图中的黑色虚线是当前分段起点到目标的参考直线，彩色线是实际记录的规划/运动轨迹，
都不是预先保存并回放的路径。

## 3. 阶段演进

### 阶段 0：基础链路和问题定位

最初目标是 Ubuntu 22.04 + ROS 2 Humble 下使用 TurtleBot3 RGB-D 完成室内点到点避障。
早期使用 NavFn/DWB 和较宽的膨胀层时，出现贴障碍、在窄口停止、绕行过大、目标改变后
仍沿旧方向行走等问题。

这一阶段的价值不是提供最终 benchmark，而是确定了后续必须同时记录的证据：Nav2 action
状态、Gazebo ground truth 轨迹、RViz/map 轨迹、末端误差和过滤地面后的 contacts。
早期失败样本不再放入正式 `results/`，相关问题保留在阶段分析文档和 Git 历史中。

主要参考：[PLANNING_ANALYSIS.md](../01_基础环境与问题分析/PLANNING_ANALYSIS.md)、[PARAMETERS.md](../01_基础环境与问题分析/PARAMETERS.md)。

### 阶段 1：Smac + RPP 的 0.45/0.55 基准

改进内容：

- 用 SmacPlanner2D 代替原先更容易产生不稳定绕行的 NavFn 路径；
- 用 Regulated Pure Pursuit 替代 DWB，增加前视跟踪和碰撞预测；
- 对 `inflation_radius=0.45 m` 和 `0.55 m` 各做三次 A->B 回归；
- 将“无非地面物理接触”设为硬门槛，满足后再比较时间和路径长度。

0.45 组平均 wall 为 `114.913 s`、Gazebo 路径 `18.173 m`；0.55 组平均 wall 为
`116.425 s`、Gazebo 路径 `18.389 m`。两组均为 3/3 成功、0/3 非地面接触，之后
选择 0.45 作为后续优化基线。

### 阶段 2：目标线软偏好规划

问题：原生 Smac 在可行区域内有时会贴着障碍物边缘，绕障后回正慢，路线与目标方向
不够一致。

改进内容：新增 `GoalLineSmacPlanner`，继承 SmacPlanner2D，在每次规划调用中根据
当前 start 和 goal 计算线段，对自由栅格增加与线段距离相关的二次软代价。lethal cell、
unknown 规则、footprint、膨胀层和碰撞检查仍然优先，因此直线不是硬编码路线。

三次结果平均 wall `113.63 s`、Gazebo 路径 `17.977 m`、末端误差 `0.162 m`，
全部成功且无非地面接触。

### 阶段 3：快速目标线 v1 到 v4

问题：阶段 2 的路线已经可以到达，但在当前大场景中速度仍接近 100 s，部分运行会
选择较大的绕行弧线。

改进内容按 v1、v2、v3、v4 逐步尝试：

- 调整目标线软代价和速度平滑；
- 增大 RPP 前视，尝试让转弯提前发生；
- 调整 inflation cost scaling；
- v4 增加当前大场景的固定世界坐标分段走廊软偏好，并将目标速度提高到 `0.30 m/s`。

v4 三次平均 wall `81.07 s`、Gazebo 路径 `17.382 m`，3/3 成功、0/3 非地面接触。
它是当前 large 场景的快速历史 benchmark，但走廊 schedule 使用了该场景的几何先验，
不能作为通用未知场景算法结论。

### 阶段 4：自适应目标线，移除固定场景路线

这是从“当前场景跑得快”转向“换目标仍由算法重新规划”的关键阶段。

改进内容：

- 保留当前 start->goal 的 line bias；
- 关闭 `side_bias`、`side_bias_target_schedule` 和固定 `world_x/world_y` 先验；
- 多目标时每一段创建新的 action，并以上一段实际结束位姿作为下一段 start；
- 使用在线 RTAB-Map 地图和实时 RGB-D obstacle layer，不回放上一轮路线。

## 7. 这条演进路线的创新和限制

### 已完成的创新点

1. 在无 LiDAR 条件下用 RGB-D 点云同时支持在线建图、障碍物代价地图和碰撞监视；
2. 将起终点直线作为规划软偏好，使可行绕障后更倾向于回到目标方向；
3. 用 `side_bias=false` 明确移除大场景固定坐标走廊，避免把 benchmark 先验误写成通用能力；
4. 用多目标 action 链和左右双视图轨迹，把实时规划行为与 Gazebo 真值、RViz 地图统一记录；
5. 用改变起点和访问顺序的 9 次闭环验证，检查算法是否仍根据当前任务重新规划。

### 仍然不能宣称的内容

- 没有证明对任意未知环境都能成功；
- 没有证明深度相机在反光、透明物体、遮挡、掉帧和弱纹理环境下可靠；
