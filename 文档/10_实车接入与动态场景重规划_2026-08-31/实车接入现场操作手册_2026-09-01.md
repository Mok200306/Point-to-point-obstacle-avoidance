# WATER II-S + D435i 实车接入现场操作手册

更新时间：2026-09-01
适用项目：`/home/w417/RTAB-Map`
当前导航基础：`adaptive_goal_line_050_recovery_v13_line_tiebreaker`

## 0. 先记住一句话

第一次上实车不是“插上相机、运行一个 launch 就开始跑”。完整系统需要同时具备：

```text
D435i 通过 USB 接到运行 ROS 2 的电脑
WATER II-S 通过 Wi-Fi 或网线接到同一局域网
底盘 ROS 驱动/SDK 把 /cmd_vel_safe 转成底盘运动，并发布 /odom 和 odom→base_link
电脑中的 RTAB-Map、Nav2、RPP 和 collision_monitor 才负责感知、建图、规划和安全限速
```

当前仓库已经提供真实 D435i、RTAB-Map、Nav2、collision_monitor、只读预检、实验记录
链路和 WATER V5.1 SDK ROS 2 bridge，但没有未经确认的 WATER II-S 厂商 ROS 底盘驱动。
bridge 可以做 SDK 状态连接和受控速度转发；没有真实编码器底盘驱动时，不能直接发送导航
目标，也不能把 `/api/robot_status` 或 bridge 暂定积分结果冒充成 ROS `/odom`。

本手册只允许按照 H0→H8 逐级放行。任何一级不满足条件，都停在当前级别，不跳级。

## 1. 推荐的第一次硬件连接方式

### 1.1 推荐拓扑：笔记本/台式机作为 ROS 电脑

第一次测试建议让“运行 Docker 和 ROS 2 的电脑”直接承担计算：

```text
                         Wi-Fi 或网线
┌──────────────────────┐                         ┌─────────────────────┐
│ ROS 2 电脑            │                         │ WATER II-S 底盘      │
│ Ubuntu + Docker       │◄──────────────────────►│ 底盘控制器/厂商软件   │
│ RTAB-Map + Nav2       │                         │ 电机、编码器、急停    │
└──────────┬───────────┘                         └─────────────────────┘
           │ USB 3.0
           ▼
   ┌───────────────┐
   │ Intel D435i   │  固定在小车上，数据线接 ROS 电脑
   └───────────────┘
```

也就是说：

- 电脑要和底盘建立网络连接；
- 相机要接到运行 ROS 2 的那台电脑，而不是只接到一个没有运行 ROS 的显示器或控制平板；
- D435i 可以安装在小车上，但 USB 线必须可靠地连接到 ROS 电脑；
- 第一次测试不建议同时使用底盘厂商自带的“自动导航任务”和本项目的 Nav2。

### 1.2 如果底盘上有工控机

若 WATER II-S 已经有工控机，并且 D435i 需要接在工控机上，则 ROS 2、相机驱动和底盘
驱动应统一运行在工控机上；笔记本只通过 SSH、RViz 或远程桌面观察。不要出现以下混乱
组合：相机接在底盘工控机、Nav2 跑在笔记本、底盘驱动又跑在第三台机器，却没有确认
ROS 2 DDS 网络和 `ROS_DOMAIN_ID`。

第一次联调优先使用 1.1 的方案，链路最容易排查。确认系统稳定后，再迁移到车载工控机。

## 2. 每个设备分别负责什么

| 设备/程序 | 负责内容 | 本项目中的关键接口 |
| --- | --- | --- |
| ROS 2 电脑 | 运行 Docker、相机驱动、RTAB-Map、Nav2 和记录器 | `/map`、`/plan`、`/cmd_vel` |
| D435i | 彩色、深度、CameraInfo 和 IMU | `/camera/color/*`、`/camera/aligned_depth_to_color/*`、`/camera/imu` |
| WATER II-S | 电机、编码器、底盘急停和实际运动 | 由底盘驱动接收 `/cmd_vel_safe` |
| 厂商 ROS 驱动/SDK 适配层 | 速度协议转换、编码器里程计、底盘 TF、watchdog | 订阅 `/cmd_vel_safe`，发布 `/odom` 和 `odom→base_link` |
| `real_d435i_nav.launch.py` | 启动相机、RTAB-Map、点云、Nav2 和碰撞监视 | 不创建假里程计，不直接控制 WATER TCP |
| `water_chassis_ros_bridge.py` | 将 `/cmd_vel_safe` 受控转发到 WATER SDK，发布状态 | 默认只读；暂定 `/odom` 仅软件联调，正式模式仍需编码器 |
| 人员 | 急停监护、观察线缆和环境、确认放行 | 硬件急停必须在手边 |

底盘资料来源为 `/home/w417/文档/底盘/`。资料中记录的默认网络信息是底盘地址
`192.168.10.10`、API TCP 端口 `31001`，但现场必须再次核对实际地址、固件和驱动方式。
仓库不保存密码，也不在启动文件中主动扫描或连接该 TCP 端口。

## 3. 上电前必须准备的东西

### 3.1 人员和场地

- 至少一名操作员和一名能够立即按下硬件急停的安全监护人员；
- 平整、无台阶、无楼梯、无落差、无地毯边缘的室内地面；
- 小车周围留出足够的人工跟随空间，第一次不要在走廊拥挤处测试；
- 清除充电线、拖链、散落物和可能缠住车轮的物体；
- 第一次只允许静态障碍或空旷地面，不带动态人员到车旁做实验。

### 3.2 硬件和资料

- WATER II-S 电量足够，已从充电桩或手充线断开；
- 硬件急停按钮可触达、可确认工作；
- D435i、USB 3.0 数据线、可靠的固定支架和不遮挡视场的安装位置；
- 运行 ROS 2 的电脑、Docker 权限、显示器或远程 RViz；
- 底盘厂商 ROS 驱动/SDK 适配层的启动方法、版本和接口说明；
- 记录本、相机序列号、底盘固件版本、载荷和现场照片。

如果还没有厂商 ROS 驱动，先向设备提供方确认以下问题：

1. 是否提供 ROS 2 Humble 驱动，还是只能使用 TCP API；
2. 驱动是否订阅 `geometry_msgs/Twist`；
3. 速度输入能否配置为 `/cmd_vel_safe`；
4. 驱动是否发布 `nav_msgs/Odometry` 的 `/odom`；
5. 驱动是否发布带正确时间戳的 `odom→base_link`；
6. 编码器的轮径、轮距、左右轮方向和里程计坐标系是什么；
7. 驱动是否有命令 watchdog，断开电脑或超时后是否自动停车；
8. 硬件急停和软件急停是否独立，如何人工确认。

没有这些答案时，先做资料确认，不要让 Nav2 控车。

## 4. 相机和车体的机械安装

### 4.1 安装原则

WATER II-S 资料建议整机外廓不超过底盘约 `0.505 m` 直径、整机高度不超过约 `1.10 m`，
并且不能遮挡底盘传感器。相机要牢固、不能晃动，USB 线要固定，不能靠近车轮和万向轮。

相机默认安装参数只是仓库中的暂定值：

```text
camera_x = 0.18 m
camera_y = 0.00 m
camera_z = 0.28 m
camera_roll = 0.00 rad
camera_pitch = 0.00 rad
camera_yaw = 0.00 rad
```

这些数值不是实车标定结果。第一次运动前必须用实际安装位置替换。

### 4.2 坐标约定

本项目默认使用：

```text
base_link：车体中心，x 向前，y 向左，z 向上
camera_link：D435i 安装基座
map → odom → base_link → camera_link
```

需要测量并记录：

- `base_link` 到 `camera_link` 的 XYZ；
- 相机是否正向朝前；
- 相机俯视角、左右偏角和是否倒装；
- 车体装载本次电脑/支架后的最大外廓；
- 用于 Nav2 的实际 footprint，而不是只使用仿真 Waffle 的 footprint。

相机安装完成后，用 RViz 检查点云是否“前方是前方、地面在下方、障碍高度正确”。如果
点云方向错误，立即停止，不要靠调规划器参数掩盖 TF 问题。

## 5. 电脑和底盘的网络连接

WATER II-S 资料给出两种连接方式，选择一种即可。

### 5.1 Wi-Fi

1. 打开底盘电源并等待工控机/底盘软件启动完成；
2. 电脑连接底盘广播的 `chuangze_xxxxx` Wi-Fi；
3. 密码向设备提供方确认，不写入 Git 仓库；
4. 在电脑上查看网络地址：

```bash
ip addr
```

5. 现场确认底盘实际 IP。若仍为默认地址，可只做基础连通性检查：

```bash
ping -c 3 192.168.10.10
```

底盘监控页面资料中的地址是 `http://192.168.10.10:9001`。这个页面只用于查看电量、
急停、运行状态和设备信息；不要在厂商页面同时下发自动移动任务。

### 5.2 网线

1. 用网线把电脑与底盘网口直连，或接到同一个交换机；
2. 电脑网卡设置为与底盘同一网段，例如底盘为 `192.168.10.10` 时，电脑可临时使用
   `192.168.10.20/24`；
3. 确认电脑没有同时连接会产生路由冲突的其他实验网络；
4. 只做 `ping` 和 ROS 图检查。

不要使用 `nmap`、`nc`、`telnet` 等方式扫描或试探 `192.168.10.10:31001`。TCP API 只应
由经过审核的底盘驱动调用，不能由本项目 launch 或人工命令直接试车。

## 6. ROS 接口必须先成立

在正式启动前，目标接口是：

```text
/odom (nav_msgs/Odometry)       底盘驱动发布
odom → base_link                底盘驱动发布
base_link → camera_link         实车 launch 的静态安装 TF
/camera/color/image_raw         D435i 发布
/camera/color/camera_info       D435i 发布
/camera/aligned_depth_to_color/image_raw
/camera/aligned_depth_to_color/camera_info
/camera/imu                     D435i 联合 IMU发布
/camera/cloud                   点云节点发布
/camera/obstacles               障碍物处理节点发布
/camera/ground                  地面点云发布
/map                            RTAB-Map 在线地图发布
/plan                           Nav2 全局路径发布
/cmd_vel                        Nav2/velocity_smoother 输出，仅进入 collision_monitor
/cmd_vel_safe                   collision_monitor 输出，底盘唯一速度入口
```

速度链路必须严格是：

```text
Nav2 → /cmd_vel → collision_monitor → /cmd_vel_safe → 底盘驱动 → 电机
```

底盘不得直接订阅 `/cmd_vel`。`/cmd_vel_safe` 也不是“绕过安全模块的手动控制口”，它是
经过 collision_monitor 的输出口；人工急停仍然必须独立可用。

特别注意：

- `/api/move` 是 WATER 自己的地图导航接口，不能与本项目 Nav2 同时作为运动控制器；
- `/api/robot_status` 的 `current_pose` 是厂商状态，不等于标准 ROS `/odom`；
- 本项目的 `real_navigation_trial.py` 只发送 Nav2 `NavigateToPose` action，不创建直接
  的 Twist publisher，也不调用 WATER TCP API；
- 没有 `/odom`、`odom→base_link` 或 `/cmd_vel_safe` 底盘订阅者，就不发送目标。

## 7. 分级启动流程

### H0：断电检查和急停确认

上电前检查：

- 车轮和万向轮没有被卡住；
- 相机支架、电脑、USB 线没有松动；
- 充电线已经拔掉，底盘不在充电状态；
- 硬件急停按钮可触达，操作员知道按下后的状态；
- 小车周围没有人或物体处于危险距离；
- 当前没有 Gazebo 仿真、没有厂商自动导航任务。

任何一项不确定，都停在 H0。

### H1：只验证 D435i，不让车运动

先启动容器和构建项目：

```bash
cd /home/w417/RTAB-Map
sg docker -c './scripts/start.sh'
sg docker -c 'docker compose exec -T ros2 bash -lc "source /opt/ros/humble/setup.bash && cd /workspaces/rtabmap_tb3_nav && colcon build --symlink-install"'
```

可以先单独启动 RealSense 驱动，具体参数以当前安装包的 `--show-args` 为准：

```bash
sg docker -c 'docker compose exec -T ros2 bash -lc "source /opt/ros/humble/setup.bash && ros2 launch realsense2_camera rs_launch.py --show-args"'
```

如果要做独立相机测试，确认参数后可以在 H1 单独启动相机；它只用于检查图像，不会让
底盘运动。进入 H4 前，必须在这个相机终端按 `Ctrl+C`，确认独立相机节点已经退出，
因为 H4 的 `real_d435i_nav.launch.py` 会再次启动 D435i。不要同时启动两份 RealSense
launch。也可以跳过独立相机测试，直接在 H4 由完整实车 launch 启动相机。检查：

```bash
docker compose exec -T ros2 bash -lc "source /opt/ros/humble/setup.bash && ros2 topic list | rg '/camera/(color|aligned_depth_to_color|imu)'"
docker compose exec -T ros2 bash -lc "source /opt/ros/humble/setup.bash && ros2 topic echo /camera/color/camera_info --once"
docker compose exec -T ros2 bash -lc "source /opt/ros/humble/setup.bash && ros2 topic echo /camera/aligned_depth_to_color/camera_info --once"
```

H1 通过条件：彩色、深度、CameraInfo、IMU 有数据；相机不掉线；没有 Gazebo 同名 topic。

### H2：只启动底盘驱动，不让 Nav2 控车

启动厂商 ROS 驱动或已经审核的 SDK 适配层。当前仓库的 WATER bridge 不是编码器里程计
驱动，不能跳过这一项。仓库没有假定具体包名，现场命令应替换为设备提供方给出的真实
命令，例如：

```bash
source /opt/ros/humble/setup.bash
source <底盘驱动工作空间>/install/setup.bash
export ROS_DOMAIN_ID=0
ros2 launch <厂商底盘包> <底盘驱动启动文件>.launch.py
```

此时只检查，不发送速度：

```bash
ros2 topic echo /odom --once
ros2 topic hz /odom
ros2 run tf2_ros tf2_echo odom base_link
ros2 topic info /cmd_vel_safe -v
```

H2 通过条件：`/odom` 类型为 `nav_msgs/Odometry`，频率连续稳定，时间戳在增长，
`odom→base_link` 可查到，底盘处于 idle/停止状态。若驱动只发布厂商 JSON 状态而没有
`/odom`，先完成适配层，不能进入 Nav2。WATER bridge 的 `allow_provisional_odom=true`
只允许用于本机 mock 或软件联调，不能满足 H2 的正式放行条件。

### H3：底盘低速运动和停止验证

H3 不启动 Nav2。使用厂商明确提供的人工控制/低速测试方式，验证：

1. 极低速直行；
2. 原地左转和右转；
3. 松开控制后的软件停止；
4. 按硬件急停后的立即停止；
5. 断开控制链路或 watchdog 超时后的停止。

不要用未经审查的 `ros2 topic pub /cmd_vel_safe` 命令代替底盘安全测试，也不要人工直接
调用 `/api/joy_control` 作为长期驱动。H3 必须保留底盘驱动版本、速度上限、急停记录。

### H4：启动本项目真实导航链并运行只读预检

H4 之前必须先启动 H2 的底盘驱动，并确认 H3 停止测试通过。然后在项目目录准备独立的
运行时快照目录：

```bash
cd /home/w417/RTAB-Map
mkdir -p 实车记录/20260901_H4_预检_v13
```

启动真实导航链。下面的 `camera_serial`、相机外参和 footprint 必须替换为实测值；命令中
不应继续使用暂定值进行正式运动。尖括号只是占位符，不能原样复制到 shell。第一次建图
建议使用一个新的数据库文件，避免打开或覆盖其他实验的地图：

```bash
sg docker -c 'docker compose exec ros2 bash -lc "source /opt/ros/humble/setup.bash && source /workspaces/rtabmap_tb3_nav/install/setup.bash && ros2 launch rtabmap_tb3_nav real_d435i_nav.launch.py use_sim_time:=false online:=true localization:=false reset_db:=false database_path:=/tmp/ros_home/.ros/rtabmap_real_20260901_H4.db navigation_profile:=adaptive_goal_line_050_recovery_v13_line_tiebreaker camera_serial:=<D435I序列号> camera_x:=<实测x> camera_y:=<实测y> camera_z:=<实测z> camera_roll:=<实测roll> camera_pitch:=<实测pitch> camera_yaw:=<实测yaw> runtime_snapshot_dir:=/workspaces/rtabmap_tb3_nav/实车记录/20260901_H4_预检_v13"'
```

如果该数据库文件以前已经使用过，不要直接加 `reset_db:=true` 试图解决问题；先停机
并备份/更换数据库路径。`reset_db` 是明确的破坏性选项，只能在确认不需要旧地图时使用。

第一次启动时 `rviz:=true`、`rtabmap_viz:=false` 即可；不要在仿真仍运行时启动该文件。
默认实车限制为线速度 `0.12 m/s`、角速度 `0.35 rad/s`，当前 v13 只表示规划基础，不能
把仿真速度 `0.28 m/s` 直接当作实车首轮速度。

另开终端运行只读预检：

```bash
cd /home/w417/RTAB-Map
./scripts/real_robot_preflight.sh \
  --duration 8 \
  --output 实车记录/20260901_H4_预检_v13/preflight.json
```

只有现场人员已经确认硬件急停可用、周围安全，并且希望把人工确认写入报告时，才追加
`--estop-confirmed`。该参数只记录确认，不会替你按急停，也不会发送运动命令。

H4 通过条件：预检报告的 `passed` 为 true，且同时满足：

- `/odom`、相机、点云、`/map` 类型和数据正常；
- `map→odom`、`odom→base_link`、`base_link→camera_link` 均可用；
- Nav2、RTAB-Map、相机和 collision_monitor 的 `use_sim_time` 均为 false；
- `/cmd_vel` 只有 collision_monitor 订阅者；
- `/cmd_vel_safe` 有 collision_monitor 发布者和底盘驱动订阅者；
- ROS 图中没有 Gazebo；
- 硬件急停已由人确认，而不是由软件假定。

预检失败时不要发送导航目标。常见含义：

| 现象 | 处理 |
| --- | --- |
| 没有 `/odom` | 底盘驱动未启动、网络不通或尚未完成 ROS 适配 |
| 没有 `odom→base_link` | 驱动没有发布 TF，或 frame 名称不一致 |
| 没有 CameraInfo/深度 | D435i、USB 3.0、驱动参数或带宽问题 |
| 没有 `base_link→camera_link` | 先测量并修正相机安装 TF |
| `/cmd_vel_safe` 没有底盘订阅者 | 底盘尚未接入安全速度入口 |
| 出现 Gazebo 节点/topic | 关闭仿真，避免 topic 和 TF 混用 |
| `use_sim_time=true` | 停止实体测试，检查 launch 或底盘节点参数 |

### H5：点云、TF 和安全速度路由目视验收

在 RViz 中至少检查：

- Fixed Frame 使用 `map`；
- 机器人模型/TF 的朝向正确；
- 点云前方、地面和障碍物高度正确；
- `/camera/ground` 主要表示地面，`/camera/obstacles` 表示可避障物；
- 局部代价地图范围内没有整片错误障碍或大片空洞；
- 机器人 footprint 包住真实车体和本次装载物；
- 相机线缆和上装没有进入点云造成的假障碍。

可做只读频率检查：

```bash
ros2 topic hz /odom
ros2 topic hz /camera/color/image_raw
ros2 topic hz /camera/aligned_depth_to_color/image_raw
ros2 topic hz /camera/cloud
ros2 topic info /cmd_vel -v
ros2 topic info /cmd_vel_safe -v
ros2 run tf2_ros tf2_echo base_link camera_link
```

如果 H5 不通过，不能进入 H6。

## 8. 第一次静态导航：H6

### 8.1 选择目标

第一次只在空旷平地做约 1 m 的短目标。目标必须使用当前 `map` 坐标系，不要直接套用
Gazebo 世界的坐标。先在 RViz 中确认机器人当前位置和目标点，再确定 `x、y、yaw`。

如果 RTAB-Map 刚启动且初始位置确实被设为 `map` 原点，可以把 `x=1.0、y=0.0` 作为
示例；如果当前地图原点或朝向不同，必须以 RViz 显示的 `map` 坐标为准。

### 8.2 启动记录器并发送 Nav2 目标

记录器只发送 `NavigateToPose` action，并记录 `/odom`、全局路径、速度链路、地图、
costmap 和相机消息。每次试验使用全新的 label：

```bash
cd /home/w417/RTAB-Map
./scripts/real_navigation_trial.sh \
  --x 1.0 --y 0.0 --yaw 0.0 --frame map \
  --label 20260901_H6_空旷直线_01 \
  --profile adaptive_goal_line_050_recovery_v13_line_tiebreaker \
  --output-dir /workspaces/rtabmap_tb3_nav/实车记录 \
  --runtime-snapshot-dir /workspaces/rtabmap_tb3_nav/实车记录/20260901_H4_预检_v13 \
  --timeout-seconds 120
```

执行期间：

- 操作员站在硬件急停旁边并跟随小车；
- 不在小车旁放动态障碍物；
- 发现姿态突变、地图漂移、点云方向错误或异常加速，立即按硬件急停；
- 不用 Ctrl+C 代替正在运动时的硬件急停；
- 试验失败也要保留目录和失败原因，不能覆盖后一次记录。

H6 通过条件：约 1 m 空旷目标能够低速到达，速度不超过实车初始上限，轨迹和终点误差
可记录，人工能够随时停止，且没有碰撞或急停异常。

## 9. 后续静态验收：H7 和 H8

### H7：单个静态箱体

在 H6 通过后，只放置一个尺寸明确、深度可见的静态箱体。先做较宽绕行，不要把箱体贴
在车体安全边界附近。记录：

- 箱体尺寸和位置；
- 车体载荷、相机外参和 footprint；
- 目标坐标；
- `/odom` 轨迹、规划路径、`/cmd_vel` 与 `/cmd_vel_safe`；

- 碰撞、急停、人工观察或视频/rosbag证据。

真实设备没有 Gazebo contacts。`contacts.yaml` 中的 `null` 只能表示当前没有自动物理
contacts 证据，不能写成“0 碰撞”。

### H8：多次静态室内点到点

逐步增加目标距离和障碍布局，仍然只用当前 v13 基础，不能把 large 场景的固定世界坐标
走廊、固定 waypoint 或 v4 先验迁移到实车。达到论文规定的重复次数并完成失败统计后，
才考虑动态障碍实车。

动态实车的第一目标仍是“危险时可靠减速/停车且不碰撞”，不是一开始就要求一定绕过
动态行人。

## 11. 正常结束和紧急停止

### 正常结束

1. 确认机器人已经停止并处于 idle；
2. 关闭记录器或等待 action 正常结束；
3. 在启动真实导航的终端按 `Ctrl+C`；
4. 停止底盘 ROS 驱动；
5. 最后按底盘手册执行关机，不要在运动中直接断电；
6. 保存并检查本次记录目录。

### 紧急情况

如果机器人突然运动、速度异常、TF 跳变、点云方向错误或即将碰撞：

1. 立即按硬件急停；
2. 人员远离轮子和车体夹缝；
3. 不要先尝试在终端猜测命令；
4. 急停后再停止 ROS launch 和底盘驱动；
5. 保留日志、视频、metrics 和现场照片；
6. 未完成原因分析前，不得再次上电重复实验。

## 12. 当前项目的明确边界

- 当前基础 profile 是四点闭环 v13：`adaptive_goal_line_050_recovery_v13_line_tiebreaker`；
- `adaptive_goal_line_045` 只作为通用对照和旧动态场景历史 profile；
- `fast_goalline_045_v4` 的 large 场景固定走廊不进入新场景和实车；
- 当前仓库未确认 WATER II-S 的厂商 ROS `/odom` 驱动，不能把 API 状态直接代替；
- 当前 launch 的相机外参和 footprint 是可配置的暂定入口，必须现场实测替换；
- 真实实车没有 Gazebo contacts，真实碰撞必须依赖硬件事件、人工记录、视频或 rosbag；
- 没有真实设备在线前，实车成功率、耗时、轨迹和 contacts 都是“未测”；
- RPP 和 collision_monitor 能完成静态跟踪、减速和停止保护，但不等于动态障碍跟踪、
  Kalman 预测或动态局部规划。
