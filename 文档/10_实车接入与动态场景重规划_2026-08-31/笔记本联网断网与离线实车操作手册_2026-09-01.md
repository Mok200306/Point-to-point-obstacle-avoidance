## 1. 先给结论

### 1.1 正确的现场结构

第一次真实接入时，移动笔记本承担全部 ROS 2 计算，D435i 接笔记本，笔记本通过局域网接
WATER II-S：

~~~text
                           底盘局域网
┌───────────────────────────┐       Wi-Fi 或网线       ┌─────────────────────┐
│ 移动笔记本                 │◄───────────────────────►│ WATER II-S 底盘      │
│ Docker / ROS 2 Humble     │                         │ 电机、编码器、急停   │
│ RealSense                  │                         │ 厂商底盘驱动         │
│ RTAB-Map + Nav2            │                         └─────────────────────┘
│ collision_monitor          │
└──────────────┬────────────┘
               │ USB 3.0 数据线
               ▼
       ┌─────────────────┐
       │ Intel D435i     │
       │ 固定在小车上     │
       └─────────────────┘
~~~

台式机第一次不参与控制链路，也不能同时运行 Gazebo、ROS 2 或另一个底盘控制节点。D435i
必须直接接运行 ROS 2 的笔记本；“笔记本只负责显示、台式机负责 ROS、相机又接第三台电脑”
的组合需要额外配置 DDS 和时钟，暂不作为第一次现场方案。

### 1.2 公网不是现场导航的必要条件

现场真正需要的连接只有：

~~~text
笔记本 ── USB ── D435i
笔记本 ── 底盘局域网 ── 192.168.10.10:31001（实际值以现场确认为准）
~~~

公网只用于克隆代码、下载 Docker/ROS/Python 依赖、安装工具、上传数据和推送 GitHub。
RTAB-Map、Nav2、RealSense、WATER SDK、ROS 2 通信和本地 rosbag 都可以在没有互联网时运行。

“离线运行”不等于把底盘网络断开：正式实车导航必须保持笔记本与底盘的局域网连接，只是
不连接互联网。

### 1.3 一块无线网卡时的标准时序

~~~text
公网阶段：下载、构建、安装、mock 自测、备份
        ↓ 机器人停止
切换阶段：断开公网 Wi-Fi，连接底盘 Wi-Fi
        ↓
离线现场：保持底盘 Wi-Fi，启动 D435i/ROS/底盘驱动并本地记录
        ↓ 机器人安全停止、所有节点关闭
恢复阶段：断开底盘 Wi-Fi，重新连接公网
        ↓
分析阶段：回放数据、更新文档、commit、push
~~~

实验进行时不能把底盘 Wi-Fi 断开；否则笔记本会同时失去底盘控制和状态连接。

### 1.4 需要现场保留公网时

优先使用第二条网络：

- 笔记本 Wi-Fi 连接底盘，手机 USB 网络共享提供公网；
- 笔记本 Wi-Fi 连接底盘，第二个 USB Wi-Fi 网卡连接公网；
- 网线连接底盘，内置 Wi-Fi 连接公网；
- 网线连接底盘，手机 USB 网络共享提供公网。

必须用路由命令确认底盘地址和公网地址走不同接口，不能只看图形界面的“已连接”。

## 3. 公网准备阶段：先把笔记本准备完整

这一阶段必须在笔记本能访问公网时完成。机器人不上电或保持停止。

### 3.1 获取项目

~~~bash
cd /home/<笔记本用户名>
git clone git@github.com:Mok200306/Point-to-point-obstacle-avoidance.git RTAB-Map
cd /home/<笔记本用户名>/RTAB-Map
git status --short
git log -1 --oneline
~~~

如果是从 U 盘复制项目，也要执行最后两条检查。不要用 git add . 把用户自己的任务书、
密码或私有配置一并加入版本库。

### 3.2 检查宿主机工具

~~~bash
cd /home/<笔记本用户名>/RTAB-Map
git status --short
git rev-parse HEAD
git remote -v
docker --version
docker compose version
docker info
~~~

预期 Docker daemon 和 Compose 都可用。若 Docker 权限不足，先处理当前用户的 Docker 组
权限并重新登录；不要在现场运动阶段临时安装 Docker。

### 3.3 使用 CPU Compose 构建

移动笔记本默认不假设有 NVIDIA GPU，所有命令都显式带 CPU 覆盖：

~~~bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.cpu.yml \
  config --quiet
~~~

无输出且返回码为 0 后再构建：

~~~bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.cpu.yml \
  build

docker compose \
  -f docker-compose.yml \
  -f docker-compose.cpu.yml \
  up -d

docker compose \
  -f docker-compose.yml \
  -f docker-compose.cpu.yml \
  ps
~~~

如果需要 RViz2：

~~~bash
xhost +si:localuser:"$(id -un)" >/dev/null 2>&1 || true
~~~

Compose 使用 host network、host IPC，并将 /dev/bus/usb 映射进容器，这是容器访问底盘
局域网和 D435i 的基础。

### 3.4 在容器内编译 ROS 工作区

~~~bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.cpu.yml \
  exec -T ros2 bash -lc '
    source /opt/ros/humble/setup.bash
    cd /workspaces/rtabmap_tb3_nav
    colcon build --symlink-install
  '
~~~

构建完成后做 SDK 离线自测。它启动本机 mock，不访问真实底盘：

~~~bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.cpu.yml \
  exec -T ros2 bash -lc '
    cd /workspaces/rtabmap_tb3_nav/water_chassis_sdk_v5_1_cn_complete/water_chassis_sdk_cn_v5_1
    python3 tools/self_test.py
  '
~~~

预期最后出现：

~~~text
WATER V5 self-test: PASS
~~~

若失败，先在公网阶段修复镜像、依赖或工作区，不要把未解决的构建问题带到实车旁边。

### 3.5 检查 D435i USB

D435i 固定在车上，USB 3.0 数据线直接连接笔记本。第一次不要使用普通无源 Hub；线长不够
时使用可靠的有源 Hub，并把线固定在车体上，远离车轮。

宿主机检查：

~~~bash
lsusb
lsusb -t
~~~

容器检查：

~~~bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.cpu.yml \
  exec -T ros2 bash -lc 'command -v lsusb >/dev/null && lsusb || echo "容器内未安装 lsusb；以宿主机 lsusb 和 RealSense topic 为准"'
~~~

预期宿主机和容器都能看到 Intel RealSense；lsusb -t 最好显示 USB 3（5000M）链路。记录
相机序列号、分辨率和线缆方式。正式 run 的 世界快照.yaml 或阶段文档中必须补齐这些信息。

### 3.6 检查本地离线资源和磁盘

~~~bash
docker image inspect rtabmap-tb3:humble >/dev/null && echo "local image ready"
df -h /home/<笔记本用户名>/RTAB-Map
~~~

断网前必须确认本地已有：

~~~text
[ ] Docker 镜像
[ ] colcon build 产物
[ ] RealSense ROS 2 包
[ ] WATER SDK 和 Python 依赖
[ ] 厂商底盘驱动/安装包和启动方法
[ ] v13 launch、参数、行为树、bridge
[ ] 本次结果目录和足够磁盘空间
~~~

如果要在完全没有网络的地点备用迁移 Docker 镜像：

~~~bash
docker save \
  -o /media/<用户名>/<U盘挂载点>/rtabmap-tb3-humble_20260901.tar \
  rtabmap-tb3:humble
~~~

恢复时：

~~~bash
docker load -i /media/<用户名>/<U盘挂载点>/rtabmap-tb3-humble_20260901.tar
docker image inspect rtabmap-tb3:humble >/dev/null
~~~

镜像和原始 bag 可能很大，先确认 U 盘容量。不要把底盘密码打包进镜像或备份。

## 4. 断开公网前的明确时刻

满足以下条件后才能从公网切到底盘网络：

~~~text
[ ] 当前没有机器人运动
[ ] 厂家自动导航/遥控任务已关闭
[ ] 完整 launch、bridge 和底盘驱动没有等待关键控制动作
[ ] Docker 镜像已构建，工作区已编译
[ ] SDK mock 自测通过
[ ] D435i 已被宿主机和容器识别
[ ] 厂商底盘驱动已本地准备
[ ] 本次实验目录和磁盘空间已准备
[ ] 已记录公网连接名、底盘 SSID、底盘 IP 和无线接口名
~~~

在单无线网卡上，先断开公网，再连接底盘 Wi-Fi。若要保留公网，先配置第二条网络并验证
路由，再进入现场。进入 P1 后不要执行 apt install、docker build、git pull 或其他
依赖互联网的命令；缺依赖就安全停机、恢复公网后补齐。

## 5. 切换到底盘局域网

### 5.1 查看当前网络

在 [宿主机]：

~~~bash
nmcli device status
nmcli connection show --active
ip -br addr
ip route
~~~

记下无线接口，例如 wlp2s0，和当前公网连接名。

### 5.2 单 Wi-Fi 连接底盘热点

推荐 Ubuntu 图形界面选择底盘 SSID，以免密码写入 shell 历史。命令行可交互输入密码：

~~~bash
nmcli connection show --active
nmcli connection down id "<公网连接名>"
nmcli --ask device wifi connect "<底盘SSID>" ifname <无线接口>
~~~

确认底盘网络：

~~~bash
ip -br addr
ip route
ip route get 192.168.10.10
ping -c 3 -W 1 192.168.10.10
~~~

预期笔记本在底盘网段，例如 192.168.10.x/24，到 192.168.10.10 的路由走底盘无线接口。
如果：

~~~bash
ip route get 1.1.1.1
~~~

显示不可达，是单 Wi-Fi 离线模式的预期，不是底盘故障。此时 ROS 2、D435i 和本地 Docker
仍可运行。

### 5.3 网线接底盘、Wi-Fi 保留公网

只有厂家确认网口和 IP 后使用。假设底盘为 192.168.10.10，笔记本底盘网卡为
<底盘网卡>，临时地址为 192.168.10.20/24：

~~~bash
nmcli connection add type ethernet \
  ifname <底盘网卡> \
  con-name water-direct \
  ipv4.method manual \
  ipv4.addresses 192.168.10.20/24 \
  ipv4.never-default yes \
  ipv6.method disabled

nmcli connection up water-direct
ip route get 192.168.10.10
ip route get 1.1.1.1
ping -c 3 -W 1 192.168.10.10
~~~

理想结果：底盘地址走网线，公网地址走 Wi-Fi 或手机 USB 网络。实验结束后只关闭明确创建
的连接：

~~~bash
nmcli connection down water-direct
~~~

不要删除未知的系统网络连接。

### 5.4 双网络路由检查

~~~bash
ip -br addr
ip route
ip route get 192.168.10.10
ip route get 1.1.1.1
~~~

理想形式：

~~~text
192.168.10.10  dev <底盘接口>  src 192.168.10.20
1.1.1.1        dev <公网接口>  src <公网地址>
~~~

若两个目标走错接口，先修正 NetworkManager 默认路由和连接优先级，再启动 ROS，不要反复
重启节点碰运气。

### 5.5 网络安全边界

~~~text
允许：ip、ip route、ping 已知地址、查看厂家管理页面、ROS 状态 topic
不做：nmap 扫描、nc/telnet 试探端口、修改密码、调用未知 API、发送运动命令
~~~

31001 是资料中的厂家 TCP 端口；端口调用由审核过的 bridge 或厂家驱动完成，不由人工
端口扫描验证。

## 7. H0：上电前物理安全

H0 不启动导航、不发送速度。

~~~text
[ ] 场地平整，无楼梯、台阶、地毯边缘和落差
[ ] 车轮、万向轮和底盘外壳没有卡住
[ ] D435i 支架牢固，镜头无遮挡
[ ] USB 线远离驱动轮和夹线位置
[ ] 笔记本固定在车上或由安全人员稳定携带
[ ] 充电线已拔出，底盘不在充电状态
[ ] 硬件急停可触达，专人站在急停旁
[ ] 厂家自动导航、遥控和旧控制程序已停止
[ ] 台式机没有运行 Gazebo、ROS 2 或第二个底盘控制节点
[ ] 第一轮只使用空旷静态区域
~~~

建议上电顺序：接 D435i → 连接底盘局域网 → 确认停止和急停 → 按厂家手册给底盘上电 →
等待底盘控制器完成启动 → 启动底盘驱动和本项目 ROS。不要在车可能运动时切换网络、拔
USB 或重建容器。

## 8. H1：只检查 D435i

H1 可以先在没有底盘网络时完成；正式现场仍要在相机最终安装位置复核。

### 8.1 查看参数

在 [Docker]：

~~~bash
ros2 launch realsense2_camera rs_launch.py --show-args
~~~

### 8.2 独立启动相机

使用实际序列号；若只有一台相机且序列号未记录，可暂时去掉 serial_no：

~~~bash
ros2 launch realsense2_camera rs_launch.py \
  camera_name:=camera \
  camera_namespace:=camera \
  serial_no:=<D435i序列号> \
  enable_color:=true \
  enable_depth:=true \
  enable_sync:=true \
  enable_gyro:=true \
  enable_accel:=true \
  unite_imu_method:=2 \
  align_depth.enable:=true \
  pointcloud.enable:=false
~~~

另开终端检查：

~~~bash
ros2 topic list | grep -E '/camera/(color|aligned_depth_to_color|imu)'
ros2 topic echo /camera/color/camera_info --once
ros2 topic echo /camera/aligned_depth_to_color/camera_info --once
ros2 topic hz /camera/color/image_raw
ros2 topic hz /camera/aligned_depth_to_color/image_raw
~~~

每个 hz 观察约 10 秒后按 Ctrl+C。预期图像和 CameraInfo 持续有数据，IMU topic 能收到消息。

独立 H1 完成后，在相机前台按 Ctrl+C，确认节点退出。H4 的完整实车 launch 会再次启动
D435i，不能同时运行两份 RealSense launch。

## 9. H2：底盘状态、真实编码器 /odom 和 TF

### 9.1 正式接口门槛

厂家驱动或审核适配层必须提供：

~~~text
/odom                 nav_msgs/Odometry，来自真实编码器或可靠融合
odom → base_link      连续、时间戳正常
订阅 /cmd_vel_safe    经过 collision_monitor 的唯一安全速度入口
watchdog              ROS/网络断开或超时后自动停车
~~~

/api/robot_status、current_pose 和 bridge 的 SDK 速度积分结果都不能作为正式实车 /odom。
没有真实 odom 时，只能做状态诊断和传感器采集，不得发送 Nav2 目标。

### 9.2 bridge 只读诊断

底盘网络已经确认后，可启动本项目 bridge 读取状态；它不会转发速度，也不会发布暂定 odom：

~~~bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.cpu.yml \
  exec ros2 bash -lc '
    source /opt/ros/humble/setup.bash
    source /workspaces/rtabmap_tb3_nav/install/setup.bash
    ros2 launch rtabmap_tb3_nav water_chassis_bridge.launch.py \
      water_robot_host:=<底盘实际IP> \
      water_robot_port:=31001 \
      water_enable_motion:=false \
      water_allow_provisional_odom:=false
  '
~~~

另开终端：

~~~bash
docker compose \
  -f docker-compose.yml \
  -f docker-compose.cpu.yml \
  exec -T ros2 bash -lc '
    source /opt/ros/humble/setup.bash
    source /workspaces/rtabmap_tb3_nav/install/setup.bash
    ros2 topic echo /water_chassis/status --once
    ros2 topic info /cmd_vel_safe -v
  '
~~~

状态可读不等于底盘已经满足 Nav2。若同时运行厂家自动控制程序，立即停止其中一个；任何
时刻只能有一个运动控制拥有者。

### 9.3 启动厂家驱动并检查

仓库没有假定厂商包名，现场必须替换为实际命令：

~~~bash
source /opt/ros/humble/setup.bash
source <厂家底盘工作空间>/install/setup.bash
export ROS_DOMAIN_ID=0
ros2 launch <厂家底盘包> <厂家底盘启动文件>.launch.py
~~~

随后只检查：

~~~bash
ros2 topic echo /odom --once
ros2 topic hz /odom
ros2 run tf2_ros tf2_echo odom base_link
ros2 topic info /cmd_vel_safe -v
~~~

H2 只有在 /odom 类型正确、时间戳增长、TF 连续、底盘不运动、/cmd_vel_safe 有唯一订阅者
且 watchdog 已确认时才通过。若厂家驱动只输出 JSON/HTTP 状态，停在 H2。

### 9.4 唯一控制拥有者

| 现场条件 | use_water_bridge | 运动开关 | 暂定 odom |
| --- | ---: | ---: | ---: |
| 只做 SDK 状态诊断 | true 或不启动 | false | false |
| 厂家驱动控制且发布真实 odom | false | 不适用 | 不适用 |
| bridge 控制、外部节点发布真实 odom | true | true | false |
| 只有 SDK、没有真实 odom | 只能诊断 | false | false |
| 本机 mock 软件联调 | true | true | true |

绝不能让厂家运动驱动和项目 bridge 同时向底盘发控制。main.py 是厂家 SDK 示例，不是
Nav2 控制器；不要直接修改它来绕过 ROS 安全链。

## 17. 常见故障

### 17.1 连接底盘 Wi-Fi 后没有公网

单无线网卡的正常现象。保留底盘 Wi-Fi 完成现场实验；结束并安全停机后再切回公网，或
增加第二条网络。

### 17.2 底盘 IP 不通

~~~bash
ip -br addr
ip route
ip route get <底盘实际IP>
ping -c 3 -W 1 <底盘实际IP>
~~~

检查 SSID、底盘电源、实际 IP 和网段。不要扫描整个网段或直接改 IP/密码。

### 17.3 离线 docker compose up 要拉镜像

本地镜像没有准备好。恢复公网后 build，或用 docker load 恢复已保存镜像；不要在现场
临时下载依赖。

### 17.4 宿主机看到 D435i，容器看不到

~~~bash
lsusb
lsusb -t
docker compose -f docker-compose.yml -f docker-compose.cpu.yml exec -T ros2 bash -lc 'command -v lsusb >/dev/null && lsusb || echo "容器内未安装 lsusb"'
~~~

确认当前容器由 CPU Compose 创建且有 /dev/bus/usb:/dev/bus/usb 映射。车体静止时重建
容器后再检查。

### 17.5 topic 有名字但没有数据

检查是否启动了两份 RealSense、USB 是否退回 USB 2、分辨率/线缆/Hub 是否可靠。只保留一
份相机 launch。

### 17.6 bridge 能读状态但没有 /odom

这是当前已知边界。取得厂家 ROS 驱动或完成真实编码器适配，确认 odom→base_link 后再
进入 Nav2。不要开启 water_allow_provisional_odom:=true 来生成正式结果。

### 17.7 /cmd_vel_safe 没有底盘订阅者

驱动未启动、topic 名不一致或安全入口未接入。停止在 H4/H5，不能把底盘改成直接订阅
/cmd_vel。

### 17.8 发现 Gazebo 或 use_sim_time=true

停止仿真和残留节点，重新启动 real_d435i_nav.launch.py use_sim_time:=false。真实 launch
会拒绝非 false 时钟，但仍要人工检查 graph。

### 17.9 rosbag 太大

原始彩色/深度图增长很快。先停止记录并确认机器人安全，再把明确的临时 bag 移到外部盘；
不要对工作区、results/ 或整个家目录执行递归删除。

## 20. 当前边界与下一步

截至本文创建时，仓库已经有真实 D435i launch、WATER SDK ROS 2 bridge、只读预检和实车
记录器，但没有真实 WATER II-S 在线实测证据。因此：

- 实车成功率、耗时、轨迹和 contacts 均为未测；
- water_allow_provisional_odom:=true 仅限 mock/软件联调，不能用于正式实车；
- 首轮实车使用默认保守上限 0.12 m/s、0.35 rad/s，等待空旷地面实测后逐级放开；
- v13 是当前四点闭环基础，不等于把仿真速度、仿真坐标或固定走廊搬到真实场地；
- adaptive_goal_line_045 仅是对照/历史 profile；fast_goalline_045_v4 的 large 场景固定走廊
  不得迁移到新场景或实车。

TF、watchdog、急停和 /cmd_vel_safe 全部确认后，再启动完整 v13 链和约 1 m 静态目标。
静态 H8 完成前不做动态障碍实车。
