## 2. 实验设置

场景 03 由场景 02 世界复制得到，只增加一个环境因素：可检测、可重复往返的
`dynamic_obstacle` 箱体。静态墙体、障碍物、机器人尺寸、起点和目标点不变。

| 项目 | 设置 |
| --- | --- |
| 世界文件 | `indoor_obstacle_course_cross_scene_03_dynamic.world` |
| 动态模型 | `dynamic_obstacle`，`0.8×0.8×0.8 m` |
| 初始位置 | `x=-4.0 m, y=-2.8 m, z=0.4 m` |
| 运动范围 | 固定 `x=-4.0 m`，`y=-2.8…-1.0 m` |
| 速度 | `0.18 m/s`，到边界反向 |
| 规划/控制 | GoalLineSmacPlanner、Smac 栅格搜索、RPP |
| 感知/建图 | Gazebo RGB-D、RTAB-Map online SLAM、实时 global/local costmap |
| 安全层 | `nav2_collision_monitor`，输入 `/camera/cloud` |
| 物理验收 | Gazebo contacts，过滤地面接触 |

动态箱体只由 `dynamic_obstacle_driver.py` 发布速度，不向 Nav2 发布地图、路线或
waypoint。规划器仍然只接收每一段的目标坐标，并依据在线地图和 costmap 重新规划。

## 5. run_03 碰撞边界分析

`run_03` 的 `metrics.yaml` 仍记录四段 `status=4`，但
`gazebo_contacts_summary.yaml` 明确记录：

```text
collision1: "waffle::base_link::base_collision"
collision2: "dynamic_obstacle::link::collision"
collision1: "waffle::wheel_left_link::wheel_left_collision"
collision2: "dynamic_obstacle::link::collision"
```

从原始 contacts 日志读取到，机器人与动态箱体的接触发生在仿真时间约
`62.674–64.847 s`，属于 `M→N` 段。首个轮子接触记录的接触深度约为
`0.000287 m`，接触点约为 `(-3.610,-2.905,0.029) m`；这不是地面接触，也不是
归档脚本把正常地面接触误报为碰撞。

同一段的保守动态几何近似 clearance 为 `-0.2968 m`，而 `run_01`、`run_02` 的
最小值分别为 `0.3683 m`、`0.5255 m`。该近似量是机器人圆形包络与动态箱体的
时间近邻几何估计，不能代替物理 contacts；本次最终判定以 Gazebo contacts 为准。

目前证据支持的故障分类是：动态障碍在机器人绕行窗口内出现了在线感知/costmap
更新、规划重算和 RPP 局部执行之间的时序边界，导致实际 footprint 在转向过程中
擦碰箱体。仅凭三次结果还不能把责任唯一归因于深度漏检、costmap 残影、重规划
周期或控制器参数，因此本次不直接调参、不修改 profile。

停止仿真时还观察到已知的退出阶段消息：`map_padder.py` 偶尔报告
`rcl_shutdown already called`。它发生在导航结果和 contacts 归档之后，三次结果的
metrics、轨迹和 contacts 文件均已写入；该退出噪声不改变本次碰撞判定。

## 6. 阶段结论和下一步

当前可在论文中表述为：

> 在场景 02 静态布局基础上加入一个可重复往返的 Gazebo 动态箱体后，系统使用
> RGB-D 在线建图、实时 costmap、GoalLineSmacPlanner、RPP 和 collision_monitor，
> 三次四点闭环均到达全部目标；其中两次通过 Gazebo 非地面物理接触检查，一次在
> M→N 段发生短时箱体接触。

当前不能表述为：已解决动态行人避障、具备速度预测能力、真实 D435i 已验证，或
在动态环境中具有 100% 安全成功率。

下一步应使用新的诊断 label 保留现有三次结果，围绕 `M→N` 接触窗口同步记录
`/camera/cloud`、global/local costmap、`/cmd_vel`、`/cmd_vel_safe`、TF、机器人
Gazebo 真值和动态箱体真值；确认感知、代价地图、重规划、RPP 或 collision_monitor
的具体责任后，才允许提出一个单因素的新 profile。任何修复后的正式三次回归都应
写入新的结果目录，不能覆盖本报告和现有 `run_01..run_03`。
