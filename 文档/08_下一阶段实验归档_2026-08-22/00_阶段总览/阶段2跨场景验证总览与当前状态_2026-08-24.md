- 使用 Docker 内 Ubuntu 22.04 + ROS 2 Humble；主机为 Ubuntu 20.04 + RTX 4090。
- TurtleBot3 Waffle 使用模拟 RGB-D 相机，不订阅 `/scan`。
- RTAB-Map 以 `online:=true`、`localization:=false` 运行，机器人边走边建图。
- Nav2 使用 RTAB-Map 地图、RGB-D obstacle layer、GoalLineSmacPlanner 和 RPP。
- 每段目标由回归脚本在上一段完成后发送；规划器不接收预先录制的中间路径。
- 每次正式 run 都保存 `metrics.yaml`、双视角轨迹图、规划/真值 CSV、参数快照、
  世界快照和 Gazebo contacts。
- 验收条件是：全部目标段 `status=4`、非地面 contacts 为 0、数据完整；成功率不能
  只依据一张图或一次运行判断。

## 4. 场景 02：交错障碍与四点闭环

世界文件：
`src/rtabmap_tb3_nav/worlds/indoor_obstacle_course_cross_scene_02.world`

用户确认了交错障碍布局，主要任务为：

```text
M(-8.5, 0.0) -> N(8.5, 0.0) -> X(-3.0, -4.0) -> Y(5.0, 5.0) -> M(-8.5, 0.0)
```

### 4.1 失败现象和原因

早期版本在 N→X 段出现过明显南侧长回环：机器人在约 `(2.5,-4.0)` 附近无法继续
前进时，没有立即在可行方向上重新建立朝向，而是先退回到约 `(6.0,-6.0)` 再掉头。
这不是脚本给了 `(6,-6)` 途经点，而是在线地图和局部代价在不同阶段产生了分支：

1. RGB-D 逐步观察使局部障碍轮廓短时间膨胀或变成未知；
2. RPP 的前向碰撞投影拒绝当前局部曲率；
3. `allow_reversing=false` 时，控制器不能把倒车当作常规轨迹自由度；
4. 旧的全局代价在重新规划时可能选中一条“先退回再绕行”的可行分支；
5. 恢复动作和周期重规划之间没有及时把路径拉回当前目标方向。

因此该现象是在线感知、全局分支选择、局部控制和恢复链路共同作用的结果，不能
简单归因于“背了固定路线”。

### 4.2 v13 最终验收

v13 profile 为 `adaptive_goal_line_050_recovery_v13_line_tiebreaker`。它保留实时规划
和安全层，采用约 6 秒周期重规划、轻量当前起点到目标直线软偏好，并关闭未知空间
目标进度偏置、额外未知惩罚和场景专用侧向先验。

## 6. 当前算法链路

```text
模拟 RGB-D 图像/深度
        -> RTAB-Map online SLAM -> /map、map->odom
        -> /nav_map + global/local costmap
        -> GoalLineSmacPlanner（Smac 栅格搜索 + 当前目标线软偏好）
        -> RPP 局部跟踪与速度调节
        -> collision_monitor 前方减速/停止保护
        -> TurtleBot3 Waffle
```

目标线只在每次规划调用时由当前起点和当前目标计算。黑色起终点直线只用于轨迹图
对照，不是固定控制轨迹。SDF 只交给 Gazebo 做物理仿真、交给绘图程序显示障碍物，
Nav2 不读取 SDF 作为先验地图。

## 7. 当前边界

当前证据支持的表述是：系统在两个设计好的静态 Gazebo 障碍场景中，能够用 RGB-D
在线建图、实时重规划、逐段点到点导航并通过物理接触检查；在增加一个可重复运动
箱体后，三次闭环均完成目标导航，其中两次通过物理无碰撞检查。

当前证据不支持的表述是：动态环境中 100% 安全、动态行人预测与避障、任意陌生环境、
任意窄通道或真实 D435i 上都能保证成功。真实设备还需要检查深度噪声、反光/黑色物体、
相机安装 TF、底盘里程计、速度接口和急停链路。
