# 阶段 2：场景 02 M→N 规范化世界三次复测报告

日期：2026-08-22
状态：复测完成，2/3 成功；未满足进入多目标实验的 3/3 门槛

## 1. 复测目的

上一轮场景 02 的世界文件是 Gazebo 保存快照，包含顶层旧障碍物位姿、`<state>` 运行
位姿和内嵌 `waffle`。这会让启动脚本再次生成机器人时出现重复实体，且复现实验无法
明确到底使用哪一套位姿。本轮在不改变用户确认的障碍物布局前提下完成规范化：

- 将 `<state>` 中的静态模型位姿提升到顶层模型；
- 删除运行时 `<state>` 和内嵌 `waffle`，由启动脚本只生成一个机器人；
- 保留碰撞几何、尺寸、颜色以及用户实际保存的障碍物中心和方向；
- 保持 `adaptive_goal_line_045`、RGB-D 在线 RTAB-Map、Nav2、RPP 和
  `inflation_radius=0.45 m` 不变。

任务仍然是单段：

```text
M = (-8.5, 0.0) -> N = (8.5, 0.0)
```

每个 run 都重新启动 Gazebo、删除并重建在线 RTAB-Map 数据库，目标只通过
`NavigateToPose` 发送。没有给规划器提供障碍物 waypoint 或固定路线。

需要明确验证边界：`adaptive_goal_line_045` 的规划器配置仍保留了旧基准场景的
`side_bias_*` 软代价（世界坐标窗口约为 `x=-7.2..-2.5`，偏好 `y=0.95` 一侧）。
它不会回放轨迹，也不会把路径写死，但它属于场景相关的先验。因此本轮可以证明
“在线 RGB-D 建图 + Nav2 在场景02中重新规划”，不能单独作为“完全无场景先验的
未知环境泛化”证据；后续纯跨场景验证应关闭该先验或为每个场景明确记录独立 profile。

## 5. 失败分析

run_03 停在约 `(-6.093, -0.178)`，距离 N 约 `16.68 m`。该位置位于
`barrier_west` 前方；从当前姿态继续前进会进入障碍物的几何包络，因此 RPP 连续输出
`detected collision ahead`，controller patience 超时，Nav2 返回 `status=6`，随后
行为树尝试恢复。该 run 的物理 contacts 为 0，说明安全层阻止了碰撞，但没有找到可
继续的脱困动作。

run_01、run_02 则均向南侧下探到约 `y=-2.12/-2.18 m`，再向北侧绕行，最高约到
`y=5.35 m`，最终回到 N。两次成功说明在线地图和实时规划可以找到可行路线，但第三
次在第一道障碍前没有稳定地完成“提前横向脱离”，暴露出局部规划和恢复行为存在
随机性。

## 6. 验收结论

本轮达到的结论是：

- 世界文件启动链路已规范化，不再有重复 `waffle` 的复现歧义；
- RGB-D 在线建图、目标发送、实时 costmap、轨迹图和 contacts 证据链正常；
- `adaptive_goal_line_045` 在规范化场景 02 的 M→N 三次复测为 `2/3`，尚不能宣称
  场景 02 通过；
- 本轮未回放固定路径，但仍带有 `side_bias_*` 场景软先验，验证结论不能扩大为
  完全无先验的未知环境泛化；
- 由于没有达到 `3/3` 成功且非地面 contacts 全为 0 的门槛，本轮没有执行
  `M→N→X→Y→M` 多目标实验。

## 7. 下一步

下一轮应以本报告为基线，先针对西侧第一道障碍的“提前下探/恢复脱困”问题做单因素
改动，并保留本轮 `adaptive_goal_line_045` 作为可复现对照。建议优先检查：

1. 第一障碍前的局部 costmap 是否及时看到完整障碍宽度；
2. RPP 的 collision projection、lookahead 和 controller patience 是否互相冲突；
3. Nav2 `BackUp` recovery 是否真的触发并完成有效倒车；
4. 改动后仍先跑同一 M→N 三次，只有达到 `3/3` 才进入多目标实验。

禁止通过手动拖动机器人、预置 Gazebo 状态或加入固定障碍 waypoint 来“修复”失败；
否则不能再把结果解释为实时未知目标规划。
